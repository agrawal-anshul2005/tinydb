Assignment 3 — Automated Software Engineering (AutoSE), IIIT Hyderabad
Author: Anshul Agrawal (2025901015) Target Fork: agrawal-anshul2005/tinydb (edff96a) Date: 21 November 2026
Executive Summary: We designed, justified (10 versioned Nygard ADRs with 16 archived superseded versions), and built a six-stage GitHub Actions agentic SDLC workflow on TinyDB (edff96a) that converts an issue into a tested, independently reviewed pull request without ever auto-merging. Core pillars include a zero-LLM deterministic orchestrator, Property-Based Testing (PBT)-first TDD via Hypothesis, AST-based read-minimal context tools with SEARCH/REPLACE diff editing, and mathematically disjoint Builder vs. Reviewer model pools (BuilderSet ∩ ReviewerSet = ∅) across free-tier Gemini 3.x, open-weight Gemma 4, and Groq failover. Across 5 real issues (2 bugs, 2 features, 1 vague), all 4 concrete issues passed all 6 stages, passed real CI, earned Round-1 independent APPROVE, and scored 13/13 (100%) on hidden acceptance tests (0 regressions), while the vague Issue #5 halted cleanly at Stage 1—using 254,262 total tokens at $0.00 cost.

1. Architecture

Connecting an LLM to a GitHub button that opens pull requests is easy; engineering a trustworthy autonomous maintainer requires strict boundaries around what each agent sees, what permissions it holds, how stages verify work before hand-off, and how retry loops remain bounded. Our workflow in .github/workflows/autose.yml splits execution across two isolated GitHub Actions jobs per review round (bounded strictly to at most two review rounds by the Actions DAG):

  • Job 1 — Builder Pipeline (round1_build / round2_build): Runs a zero-LLM deterministic Python orchestrator (orchestrator.py) across Stages 1–5 with contents: write, pull-requests: write, issues: write, and actions: write. Specialized agents handle Requirements (RequirementsAgent + A1 skill.md), Exploration & Design (ExplorerDesignAgent + A2 ARCHITECTURE.md + Python ast repo-map tools), PBT-first TDD & Implementation (ReproAgent + CoderAgent using SEARCH/REPLACE patches), Testing (Evaluator running Hypothesis PBT + full pytest regression), and Release (DeliveryAgent opening the PR and dispatching ci.yml).
  • Job 2 — Independent Reviewer (round1_review / round2_review): Runs Stage 6 (ReviewerAgent) on a fresh ephemeral VM with contents: read only (physically incapable of pushing commits), fresh checkout of the PR HEAD commit, zero download of Stage 1–5 artifacts or reasoning traces, and a strictly disjoint model pool enforced by a runtime assertion.

Deep-Dive on the Three Decisions That Mattered Most

1. Strictly Disjoint, Job-Isolated Reviewer Independence (D8 — ADR-008 v1 → v4): Preventing rubber-stamp reviews required isolation across four layers simultaneously: (a) runner isolation via a separate GitHub Actions job (round1_review / round2_review) checking out PR HEAD fresh; (b) permission isolation granting only contents: read and pull-requests: write so pushing commits is impossible at the GitHub token layer; (c) context isolation downloading zero Stage 1–5 artifacts (no spec.md, design.md, or coder logs) while prioritizing tinydb/ production diffs ahead of tests/ diffs so long PBT files never truncate production code; and (d) mathematical model disjointness. When adding Groq failover in ADR-006 v6, we noticed overlapping fallback lists could silently collapse builder and reviewer onto the same model during a 503 cascade. In ADR-008 v4 we partitioned pools strictly—Pool A (Stages 1–5): Gemini 3.x → Groq qwen3-32b / gpt-oss-20b / llama-3.1-8b; Pool B (Stage 6): Gemma 4 (26B/31B) → Groq llama-3.3-70b-versatile / openai/gpt-oss-120b—enforced by a startup assertion (BuilderSet ∩ ReviewerSet == ∅) in stage6_review.py. Combined with a 6-point adversarial checklist requiring file/line evidence, this delivered genuine cross-family (Issues #1–#2) and cross-provider (Issues #3–#4) reviews.

2. PBT-First Hybrid Deterministic Gates & Symmetric ReproAgent Loop (D7 & D2 — ADR-007 v1 → v4, ADR-002 v4): LLM-generated unit tests routinely overfit to literal examples copied from an issue description. Making Property-Based Testing (Hypothesis @given, max_examples=50, derandomize=True, dev-only) our primary test strategy forced agents to verify universal invariants—such as query-cache isolation across arbitrary field names, generator repeatability across arbitrary lists, and key conservation under rename. Live runs exposed three real PBT-generation pitfalls that shaped our architecture: (i) Run 44884332705 failed collection (rc=2) because ReproAgent hallucinated st.recursive(..., max_depth=...); (ii) Run 44885745409 passed 233/234 tests but tripped HealthCheck.filter_too_much on st.text().filter(isidentifier); and (iii) Run 44896309810 failed because ReproAgent called db.get(doc_id) positionally instead of db.get(doc_id=doc_id). Rather than abandoning PBT, we built an AST-safe deterministic sanitizer (_harden_hypothesis_settings), a static PBT linter, a pytest --collect-only + harness-error gate, and a symmetric 3-attempt escalation loop for ReproAgent mirroring CoderAgent. Similarly, Run 44881708823 revealed that Stage 5's unfiltered gh run list read an action_required pull_request event instead of our passing workflow_dispatch CI run (44881876871), prompting the deterministic --event workflow_dispatch filter in ADR-007 v3.

3. Zero-Cost Multi-Provider Allocation & Resilient Failover (D6 & D9 — ADR-006 v1 → v6, ADR-009 v2): Operating under a strict $0 free-tier cap forced six evidence-driven iterations of ADR-006: migrating off deprecated Gemini 2.5 (v1→v2); probing live endpoints to eliminate 429-blocked gemini-4-* and 503-throttled gemini-3.8-flash (v2→v3); discovering in Run 44888379411 that standalone GitHub Models (models.github.ai) was retired even with a fine-grained PAT (v3→v5); and adding Groq Free Tier failover, trimming CoderAgent prompts below gemma-4-31b's 16,000 input-TPM cap, setting a 60-second HttpOptions socket timeout (fixing Issue #3's 10-minute hang in Run 44893738117), and formally excluding transient 429/503 provider outages from all call/token/retry budgets (ADR-009 v2). Keeping the orchestrator 100% deterministic Python (0 LLM calls) preserved daily quotas strictly for reasoning stages.

Per-Stage Pass Rates & Vague Issue #5 Behavior

Across the five final runs, Stage 1 passed on 4/5 issues (80%) and intentionally halted on vague Issue #5 (Run 44897372948). Inspecting Issue #5's uploaded spec.md confirms that our A1 Requirements Skill performed exactly as intended: it flagged two blocking [UNRESOLVED] public-API questions—Q-1 (whether incomparable types like None/str should silently evaluate to False globally across all comparison operators or via opt-in configuration) and Q-2 (whether changing operations.delete to skip missing keys violates TinyDB's existing KeyError contract)—and halted cleanly in 1 call (3,153 tokens) rather than silently shipping breaking changes. Among the 4 issues that cleared Stage 1, pass rates for Stages 2, 3, 4, 5, and 6 were 4/4 (100%), with our self-healing loops actively earning their keep: ReproAgent auto-repaired PBT harness issues on Issues #1 (2 attempts) and #3 (3 attempts), and CoderAgent self-corrected test failures via Stage 4 tracebacks on Issues #1, #2, and #3 before passing on Attempt 2 (while Issue #4 passed cleanly on Attempt 1 in 3m 20s).

Hidden Acceptance Tests & Independent Reviewer Analysis

Evaluating each open PR locally against our external hidden pytest suites (kept outside the repository during all runs) achieved 13 / 13 (100%): Issue #1 PR #8 (3/3—path cache isolation, non-mapping safety, empty-fragment root/nested matching), Issue #2 PR #17 (3/3—generator multi-doc matching, reusability, hash cache), Issue #3 PR #20 (4/4—inclusive/exclusive bounds, cache isolation across inclusive, missing/incomparable/empty-path guards), and Issue #4 PR #23 (3/3—move/remove, self-rename & overwrite, missing-key KeyError), with zero regressions against TinyDB's 228 baseline tests.

  • What the Independent Reviewers Caught & Verified: Every Stage 6 review ran in a fresh read-only runner with zero upstream traces and produced grounded, line-cited audits: on PR #8, gemma-4-26b-a4b-it verified tinydb/queries.py:499's hash tuple and LRUCache PBT coverage; on PR #17, gemma-4-31b-it verified tuple materialization before freeze() at line 484; on PR #20, Groq's openai/gpt-oss-120b audited between lines +486–+512 and correctly noted that callers are expected to pass low <= high; and on PR #23, openai/gpt-oss-120b caught a subtle implementation detail—that pop + reassign on self-rename (rename('a', 'a')) alters Python dict insertion order—and noted optional __all__ exposure.
  • Where the Reviewer Was Limited / Could Be Stricter: None of the 4 PRs triggered a blocking FIX_CODE or FIX_DESIGN Round-2 loop. While this partly reflects strong upstream PBT filtering in Stage 4 (which already eliminated functional bugs before PR creation), the reviewer on PR #23 arguably could have flagged the unnecessary pop+reassign on old_field == new_field as a minor FIX_CODE request (since Issue #4 stated "leave the document unchanged") rather than a non-blocking note. Consequently, our Round 2 re-entry jobs (round2_build → round2_review) were verified structurally in YAML/orchestrator logic rather than empirically exercised by a defective PR.

4. Hindsight

If we started again tomorrow, the first decision we would change is building a pre-flight provider health probe + cross-provider failover + strict 60-second HTTP timeout on Day 1 (what took us six revisions of ADR-006 and multiple failed runs to discover). We lost substantial engineering time discovering reactively that Gemini 2.5 was deprecated, that standalone GitHub Models was retired, that gemma-4-31b-it enforces a 16k free-tier input-TPM limit, and that google-genai lacked a default HTTP timeout (causing Issue #3's Stage 6 job to hang for 10 minutes). Second, we would pair PBT-first test generation with a deterministic AST linter and library-specific API rules (e.g., Query()[field], db.get(doc_id=doc_id)) from the very first commit rather than discovering Hypothesis's st.recursive(max_depth=...) and HealthCheck.filter_too_much failure modes during live runs.

5. Limitations and Threats to Validity

  1. Small Sample Size & Single Compact Repository (External Validity): All five evaluation issues target TinyDB (~1,500 LOC, 7 pure-Python modules). Sending full target files to CoderAgent and using Python's ast for repo_map work effortlessly at this scale, but larger or polyglot repositories would require line-range chunked editing and Tree-sitter parsing to stay within context windows and TPM limits.
  2. Round-2 Review Routing Not Empirically Exercised (Internal Validity): Because Stage 4's PBT-first loop caught functional defects before Stage 5 and all 4 concrete PRs earned Round-1 APPROVE, the round2_build → round2_review DAG transition was validated through code inspection rather than a live defective-PR round-trip.
  3. Free-Tier Provider Volatility & Privacy Constraints (Reliability / Construct Validity): We logged 27 transient 429/503 errors across the 5 final runs, causing Stage 6 to fail over from Gemma 4 to Groq's openai/gpt-oss-120b on Issues #3 and #4. While uncounted retries and disjoint failover kept reliability at 100%, model swaps introduce non-determinism across runs, and Google AI Studio's free-tier data-use terms preclude using this exact setup on private proprietary repositories.
  4. GitHub Actions Bot Identity Constraint on Review States: Because both Job 1 and Job 2 authenticate with the repository's GITHUB_TOKEN (github-actions[bot]), GitHub's API rejects --approve and --request-changes on a PR authored by the same bot identity; Stage 6 therefore posts reviews via gh pr review --comment with an explicit structured verdict banner. A dedicated GitHub App identity for Stage 6 would enable native GitHub approval/request-changes states.
  5. Residual Prompt-Injection & Sandboxing Surface: Although we avoid shell interpolation of issue text, wrap untrusted content in <untrusted_issue_data> delimiters, enforce tinydb/ + tests/ write allowlists, and execute code inside ephemeral GitHub Actions VMs, a sophisticated adversarial prompt inside an authorized issue could still bias natural-language specs, and pytest currently runs with runner network access rather than inside a docker run --network=none container.
