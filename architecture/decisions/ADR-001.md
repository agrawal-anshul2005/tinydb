# ADR 001: Specialized Role-Based Agent Decomposition (D1)

## Status
Accepted

## Context
An agentic SDLC workflow must turn a raw GitHub issue into a tested and independently reviewed pull request across six fixed stages: Requirements, Design, Implementation, Testing, Release, and Review. Using a single monolithic agent for all six stages accumulates noisy intermediate context, blurs the boundary between specifying requirements and writing code, and violates the requirement for an independent reviewer. Conversely, spawning many parallel subagents (such as an Explorer fan-out of 2–3 concurrent agents per run) adds coordination complexity and risks immediately triggering `429 RESOURCE_EXHAUSTED` rate limits on a free-tier Gemini API key, especially on a compact codebase like TinyDB (7 core modules, ~1,500 lines of Python).

## Decision
We will decompose the workflow into five specialized, sequential roles orchestrated deterministically, plus an independent sixth-stage Reviewer: `RequirementsAgent` (Stage 1), `ExplorerDesignAgent` (Stage 2), `ReproAgent` paired with `CoderAgent` inside a TDD Evaluator-Optimizer loop (Stages 3 and 4), `DeliveryAgent` (Stage 5), and a strictly isolated `ReviewerAgent` (Stage 6).

We rejected a single monolithic agent because shared conversation history causes confirmation bias during review and mixes specification with implementation. We also rejected parallel Explorer subagent fan-out for TinyDB because the repository is small enough to map deterministically with Python's `ast` module in a single pass without wasting free-tier RPM quota.

## Consequences
Positive consequences include focused system prompts per role, clean artifact boundaries (`spec.md`, `design.md`, `diff.patch`, `test_report.md`, `pr.md`, `review.md`), and TDD discipline where `ReproAgent` establishes failing acceptance tests and a baseline `status.md` before `CoderAgent` writes production edits.

Negative consequences include slightly higher prompt-engineering maintenance across multiple role files and sequential latency compared to parallel subagent execution.

Neutral consequences include the ability to evolve `ExplorerDesignAgent` into sharded parallel workers in future work if the workflow is ported to a large monorepo.
