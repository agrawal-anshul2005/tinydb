# ADR 010: Authorized Event Triggers and Per-Issue Concurrency Control (D10)

## Status
Accepted

## Context
Maintainers want to invoke the agentic SDLC workflow directly from GitHub by labeling an issue or posting a command comment, while preventing unauthorized external users on a public fork from triggering API calls or creating spam pull requests. Additionally, if a maintainer accidentally adds the label and also posts `/autose` (or posts `/autose` twice rapidly), two overlapping runs targeting the same issue would race on branch `autose/issue-<N>` and open conflicting PR updates.

## Decision
We will trigger `.github/workflows/autose.yml` on two GitHub events:
1. `issues: types: [labeled]` — executes only when `github.event.label.name == 'autose'`.
2. `issue_comment: types: [created]` — executes only when the comment is on an issue (not a PR) and starts with `/autose`.

To enforce authorization on our public fork, an explicit job-level `if:` guard verifies that `github.actor == github.repository_owner` or `author_association` is in `('OWNER', 'MEMBER', 'COLLABORATOR')`. To prevent race conditions between overlapping triggers on the same issue, the workflow declares a per-issue concurrency group: `concurrency: group: autose-issue-${{ github.event.issue.number }}` with `cancel-in-progress: false` (queuing rather than killing an active run mid-push).

We rejected `issues: [opened]` auto-triggering because unvetted or draft issues would immediately burn free-tier Gemini quota before a maintainer approves automation. We also rejected `cancel-in-progress: true` because cancelling a run mid-`git push` or mid-`gh pr create` can leave a half-written PR state.

## Consequences
Positive consequences include deliberate maintainer opt-in per issue, zero risk of unauthorized public users burning `GEMINI_API_KEY` quota, and safe serialization of concurrent triggers on the same issue without corrupting branches.

Negative consequences include one extra manual action (adding the `autose` label or commenting `/autose`) before automation starts, and queued waiting if a maintainer re-triggers while an earlier run is still executing.

Neutral consequences include noting GitHub's built-in security boundary that workflows triggered from external forks do not receive repository secrets (`GEMINI_API_KEY`), which naturally reinforces our fork-only rule.
