# ADR 009: Budgets, Transient-Error Exclusion, Timeouts, Sandboxed Execution, and Prompt-Injection Defenses (D9)

## Status
Accepted (v2 — supersedes [archive/ADR-009_v1.md](./archive/ADR-009_v1.md))

## Context
GitHub Actions workflows triggered by issues and comments operate on untrusted natural-language input and invoke external free-tier LLM APIs plus code execution (`pytest`). Without strict guardrails, a malicious or malformed issue could cause shell injection, prompt injection, runaway retry loops, or hung CI runners. Additionally, live runs `44884332705` and `44885745409` demonstrated frequent transient HTTP `503 UNAVAILABLE` demand spikes on free-tier Gemini models; penalizing provider-side outages against application-level retry or call budgets would prematurely abort healthy runs.

## Decision
We will enforce defense-in-depth across five dimensions:

1. **Untrusted-Input & Prompt-Injection Protection:** Workflow YAML never interpolates `${{ github.event.issue.title }}`, `${{ github.event.issue.body }}`, or `${{ github.event.comment.body }}` into `run:` shell scripts. Python fetches issue data via `gh issue view --json`, wraps untrusted text inside `<untrusted_issue_data>...</untrusted_issue_data>` delimiters, instructs every agent to treat enclosed text strictly as data, and restricts file edits strictly to allowlisted paths under `tinydb/` and `tests/`.
2. **Hard Budgets (Excluding Transient Provider Errors):** Every run enforces `MAX_TOKENS_PER_RUN=200000`, `MAX_LLM_CALLS_PER_RUN=20`, `MAX_REPRO_ATTEMPTS=3`, `MAX_CODER_ATTEMPTS=3`, `MAX_REVIEW_ROUNDS=2`, and a \$0 provider spending ceiling. **Crucially, transient provider errors (`429`, `500`, `502`, `503`, `504`) are NOT counted against `MAX_LLM_CALLS_PER_RUN`, `MAX_TOKENS_PER_RUN`, or any agent retry limit.** Instead, `llm.py` retries with exponential backoff (up to 3 attempts per model before moving to the next fallback model) and records outages separately under `transient_errors_uncounted` in `usage.json`.
3. **Timeouts & Stuck-Stage Halting:** GitHub Actions jobs enforce `timeout-minutes: 15` (builder) and `timeout-minutes: 10` (reviewer), and every `pytest`/subprocess call enforces a `60`–`90`s timeout.
4. **Sandboxed Execution & Human Merge Gate:** All agent-generated code and tests execute inside GitHub Actions' ephemeral, single-use `ubuntu-latest` VMs, `main` is branch-protected against direct pushes, and the workflow **never** merges any PR.
5. **Secrets Hygiene:** `GEMINI_API_KEY` and `GH_MODELS_TOKEN` live exclusively in GitHub Repository Secrets and are never logged or committed.

We rejected counting `429`/`503` outages toward call or iteration caps because transient API availability spikes are orthogonal to agent convergence.

## Consequences
Positive consequences include elimination of script-injection vulnerabilities, resilience against free-tier `429`/`503` spikes without prematurely tripping budgets, clear observability separating real agent calls from provider outages in `usage.json`, and safe ephemeral CI execution.

Negative consequences include longer wall-clock runtime during heavy provider `503` spikes due to exponential backoff retries (still strictly bounded by job `timeout-minutes: 15`).

Neutral consequences include fail-closed halting whenever real token/call budgets or 3-attempt agent caps are reached.
