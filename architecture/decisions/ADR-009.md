# ADR 009: Budgets, Timeouts, Sandboxed Execution, and Prompt-Injection Defenses (D9)

## Status
Accepted

## Context
GitHub Actions workflows triggered by issues and comments operate on untrusted natural-language input and invoke external LLM APIs plus code execution (`pytest`). Without strict guardrails, a malicious or malformed issue could perform shell injection in workflow YAML, hijack agent instructions via prompt injection, cause infinite retry loops that burn free-tier API quotas, or hang a CI runner indefinitely.

## Decision
We will enforce defense-in-depth across four dimensions:

1. **Untrusted-Input & Prompt-Injection Protection:** Workflow YAML will **never** interpolate `${{ github.event.issue.title }}`, `${{ github.event.issue.body }}`, or `${{ github.event.comment.body }}` directly into `run:` shell scripts. Instead, Python fetches issue data safely via `gh issue view --json title,body` (or passes IDs via `env:`), wraps untrusted text inside explicit `<untrusted_issue_data>...</untrusted_issue_data>` delimiters, instructs every agent in its system prompt to treat enclosed text strictly as data (never as commands), and restricts file edits strictly to allowlisted paths under `tinydb/` and `tests/` (blocking edits to `.github/`, `workflow/`, or `pyproject.toml`).
2. **Hard Budgets and Iteration Caps:** Every run enforces `MAX_TOKENS_PER_RUN=200000`, `MAX_LLM_CALLS_PER_RUN=15`, `MAX_TEST_RETRIES=2` (2 Flash + 1 escalated Pro attempt = 3 max per round), `MAX_REVIEW_ROUNDS=2`, `MIN_CALL_INTERVAL_SEC=10` with exponential backoff on HTTP `429`, and a \$0 provider ceiling via our Free-Tier Gemini key.
3. **Timeouts & Stuck-Stage Halting:** GitHub Actions jobs enforce `timeout-minutes: 15` (builder) and `timeout-minutes: 10` (reviewer), and every `pytest` / subprocess call enforces an explicit timeout (`60` seconds). If a stage fails its gate or hits a cap, it writes the failure trace to its artifact and halts cleanly for human intervention.
4. **Sandboxed Execution & Human Merge Gate:** All agent-generated code and tests execute inside GitHub Actions' ephemeral, single-use `ubuntu-latest` VMs (never on a developer workstation), `main` is branch-protected against direct pushes, and the workflow **never** merges any PR.

We rejected adding external microVMs (such as E2B) or Docker-in-Docker at this stage because GitHub Actions runners are already ephemeral VMs; we note network-disabled container sandboxing (`docker run --network=none`) as a straightforward hardening step.

## Consequences
Positive consequences include elimination of GitHub Actions script-injection vulnerabilities, protection against runaway API costs or infinite loops, containment of arbitrary test execution to ephemeral CI VMs, and prevention of unauthorized edits to CI workflows themselves.

Negative consequences include slightly slower wall-clock runs due to `MIN_CALL_INTERVAL_SEC=10` pacing and the theoretical risk that an extremely creative prompt injection in an issue could still influence requirements text despite delimiter isolation (mitigated by the independent reviewer and mandatory human merge gate).

Neutral consequences include strict fail-closed behavior: any cap exhaustion or security violation stops the workflow rather than continuing silently.
