# ADR 007 (v1): Hybrid Deterministic and Structured Gate Checks Across All Six Stages (D7)

## Status
Superseded by active [ADR-007.md](../ADR-007.md) (v2) — superseded to adopt **Property-Based Testing (PBT) with `hypothesis`** as our primary Stage 3/4 testing strategy (followed by example-based boundary tests and the full regression suite) so behavioral invariants are systematically verified rather than only hand-picked examples.

## Context
Each of the six SDLC stages must pass an explicit check before handing off to the next stage, and must halt with an explanation in its artifact if the check fails. Relying solely on LLM self-assessment ("looks good to me") invites hallucinations such as non-existent file paths, uncompilable patches, or unverified test claims. Conversely, pure static checks cannot judge whether natural-language acceptance criteria derived from a vague issue are genuinely testable.

## Decision
We will use deterministic, programmatic checks wherever ground truth exists and restrict LLM-assisted validation strictly to semantic checks, with the deterministic orchestrator (`orchestrator.py`) always making the final pass/fail transition decision:

- **Stage 1 (Requirements):** Structured schema validation verifying unique `FR-*`/`AC-*` IDs, `Given/When/Then` testability checks, zero blocking `[UNRESOLVED]` questions, and explicit `Gate Status: PASS` per `skill.md`.
- **Stage 2 (Design):** Deterministic parser verifying `design.md` names concrete repository file paths (within `tinydb/` or `tests/`) and target function/class symbols cross-checked against our `ast` `repo_map` (or marked as new).
- **Stage 3 (Implementation):** Deterministic `SEARCH/REPLACE` patch verification, non-empty `diff.patch`, `python -m compileall -q tinydb`, and `python -c "import tinydb"`.
- **Stage 4 (Testing):** Deterministic `pytest` execution confirming zero failures across both new AC/repro tests and the full TinyDB regression baseline (`status.md`).
- **Stage 5 (Release):** Deterministic `gh pr view` confirming an open PR and `gh pr checks --watch` confirming `ci.yml` passes.
- **Stage 6 (Review):** Deterministic round counter (`round <= 2`) plus structured JSON/YAML verdict block (`APPROVE`, `FIX_CODE`, or `FIX_DESIGN`) parsed from `review.md`.

## Consequences
Positive consequences include zero false passes on broken code, failing tests, or missing PR checks.

Negative consequences include example-only tests being prone to LLM "happy-path" blind spots (testing only the exact literal inputs mentioned in the issue). Version 2 upgrades Stage 4 to PBT-first testing with `hypothesis`.
