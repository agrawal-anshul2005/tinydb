# ADR 008: Job-Isolated, Fresh-Context, Cross-Family Reviewer Independence (D8)

## Status
Accepted (v3 — supersedes [archive/ADR-008_v2.md](./archive/ADR-008_v2.md) and [archive/ADR-008_v1.md](./archive/ADR-008_v1.md))

## Context
An automated code reviewer that shares conversation history, prompts, or repository write credentials with the implementer suffers from confirmation bias and tends to rubber-stamp its own patches. The assignment explicitly requires that the reviewer see only the issue, the PR diff, and the repository at the latest PR commit (with permission to read and run code, but not to push), and must not see the implementer's conversation or reasoning. After Run 4 revealed that GitHub Models (`models.github.ai`) was retired (superseding v2), we needed a live free-tier model that maintains model diversity from our Gemini 3.5 implementer.

## Decision
We will isolate Stage 6 (`ReviewerAgent`) across four independent layers:

1. **Process and Runner Isolation:** `ReviewerAgent` executes in a completely separate GitHub Actions job (`round1_review` / `round2_review`) on a fresh ephemeral `ubuntu-latest` VM with a clean `actions/checkout` at the PR HEAD commit.
2. **Permission Isolation:** The job grants only `contents: read`, `pull-requests: write`, and `issues: read`. Because `contents: write` is omitted, GitHub's `GITHUB_TOKEN` physically prevents the reviewer from pushing commits or modifying branches.
3. **Context Isolation:** The job never downloads `spec.md`, `design.md`, `context.json`, `status.md`, or coder retry logs. Its sole inputs are the original GitHub issue (`gh issue view`), the PR diff (`gh pr diff`), and the repository source at PR HEAD, plus read-only `pytest` execution.
4. **Cross-Architecture Cognitive Isolation:** While Stages 1–4 are built by proprietary **Gemini 3.x** (`gemini-3.5-flash-lite` / `gemini-3.5-flash` / `gemini-3.7-flash`), `ReviewerAgent` runs on a distinct open-weight model family — **Gemma 4 (`gemma-4-31b-it`, fallback `gemma-4-26b-a4b-it`)** — using an explicitly adversarial, 6-point checklist prompt requiring concrete file/line evidence before issuing `APPROVE`, and capable of routing blocking defects back to Stage 2 (`FIX_DESIGN`) or Stage 3 (`FIX_CODE`) for at most 2 review rounds.

We rejected running the reviewer inside the same orchestrator job (breaks least-privilege non-push enforcement and risks context leakage) and rejected GitHub Models after Run 4 verified endpoint retirement.

## Consequences
Positive consequences include platform-enforced non-push permissions, zero leakage of implementer rationalizations, cross-architecture model diversity (open-weight Gemma 4 auditing Gemini 3.x), and generous free-tier RPD availability.

Negative consequences include extra CI runner startup overhead (~30–60 seconds per review job) and the need to post reviews via `gh pr review --comment` (since GitHub rejects `--approve`/`--request-changes` from the same `github-actions[bot]` identity that opened the PR).

Neutral consequences include full transparency: every review is posted visibly on the GitHub Pull Request and uploaded as `review.md` alongside `review_usage.json`.
