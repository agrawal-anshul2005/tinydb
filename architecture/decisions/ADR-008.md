# ADR 008: Job-Isolated, Fresh-Context, Cross-Provider Reviewer Independence (D8)

## Status
Accepted (v2 — supersedes [archive/ADR-008_v1.md](./archive/ADR-008_v1.md))

## Context
An automated code reviewer that shares conversation history, model family biases, or repository write credentials with the implementer suffers from confirmation bias and tends to rubber-stamp its own patches. The assignment explicitly requires that the reviewer see only the issue, the PR diff, and the repository at the latest PR commit (with permission to read and run code, but not to push), and must not see the implementer's conversation or reasoning.

## Decision
We will isolate Stage 6 (`ReviewerAgent`) across four independent layers:

1. **Process and Runner Isolation:** `ReviewerAgent` executes in a completely separate GitHub Actions job (`independent_review`, `needs: sdlc_pipeline`) on a fresh ephemeral `ubuntu-latest` VM with a clean `actions/checkout` at the PR HEAD commit.
2. **Permission Isolation:** The job grants only `contents: read`, `pull-requests: write`, `issues: read`, and `models: read`. Because `contents: write` is omitted, GitHub's `GITHUB_TOKEN` physically prevents the reviewer from pushing commits or modifying branches.
3. **Context Isolation:** The job never downloads `spec.md`, `design.md`, `context.json`, `status.md`, or coder retry logs. Its sole inputs are the original GitHub issue (`gh issue view`), the PR diff (`gh pr diff`), and the repository source at PR HEAD, plus read-only `pytest` execution.
4. **Cross-Provider Cognitive Isolation:** While Stages 1–4 are built by Google's **Gemini 3.x** family (`gemini-3.5-flash-lite` / `gemini-3.5-flash` / `gemini-3.7-flash`), `ReviewerAgent` runs on a completely separate provider and model family — **GitHub Models `openai/gpt-4o`** (fallback `meta/llama-3.3-70b-instruct`) — using an explicitly adversarial, checklist-driven prompt requiring it to hunt for missed edge cases, TinyDB query-cache hash collisions, architectural constraint violations, security flaws, over-engineering, and missing tests, and to cite concrete evidence before issuing `APPROVE`.

We rejected running the reviewer inside the same orchestrator job (breaks least-privilege non-push enforcement and risks context leakage) and rejected using the same Gemini model for both implementation and review (shared self-preference bias and extra Gemini free-tier RPD consumption).

## Consequences
Positive consequences include platform-enforced non-push permissions, zero leakage of implementer rationalizations, true cross-provider model diversity to counter self-agreement bias, and zero Gemini quota consumed by code review.

Negative consequences include extra CI runner startup overhead (~30–60 seconds per review job), slightly stricter GitHub Models token-per-request limits on very large diffs (well within bounds for TinyDB patches), and the chance that a strict adversarial reviewer occasionally triggers a second round over minor edge cases.

Neutral consequences include clean auditability: every review is posted visibly on the GitHub Pull Request via `gh pr review` and uploaded as `review.md`.
