# ADR 008: Job-Isolated, Fresh-Context, Strictly Disjoint-Model Reviewer Independence (D8)

## Status
Accepted (v4 — supersedes [archive/ADR-008_v3.md](./archive/ADR-008_v3.md), [archive/ADR-008_v2.md](./archive/ADR-008_v2.md), and [archive/ADR-008_v1.md](./archive/ADR-008_v1.md))

## Context
An automated code reviewer that shares conversation history, model weights, or repository write credentials with the implementer suffers from confirmation bias and self-agreement. Furthermore, introducing multi-tier fallback chains for free-tier `503`/`429` resilience (`ADR-006` v6) creates a subtle independence hazard: if Stages 1–5 and Stage 6 share *any* fallback model (such as both falling back to `gemma-4-26b-a4b-it`, `gemini-3.7-flash`, or `llama-3.3-70b-versatile`), a transient outage could silently collapse builder and reviewer onto the exact same model.

## Decision
We will isolate Stage 6 (`ReviewerAgent`) across four independent layers, adding a **strictly disjoint primary + fallback model partition enforced by a runtime assertion**:

1. **Process and Runner Isolation:** `ReviewerAgent` runs in a completely separate GitHub Actions job (`round1_review` / `round2_review`) on a fresh ephemeral `ubuntu-latest` VM with a clean `actions/checkout` at the PR HEAD commit.
2. **Permission Isolation:** The job grants only `contents: read`, `pull-requests: write`, and `issues: read` (no `contents: write` — physically cannot push).
3. **Context Isolation:** The job never downloads `spec.md`, `design.md`, `context.json`, `status.md`, or coder retry logs. Its sole inputs are the original GitHub issue (`gh issue view`), the PR diff (`gh pr diff`, prioritizing `tinydb/` production files first), and the repository at PR HEAD, plus read-only `pytest` execution.
4. **Mathematically Disjoint Model Pools (`BuilderSet ∩ ReviewerSet = ∅`) + Adversarial Prompt:**
   - **Stages 1–5 Builder Pool (Set A):** Gemini 3.x (`gemini-3.5-flash-lite`, `gemini-3.5-flash`, `gemini-3.6-flash`, `gemini-3.7-flash`) → Groq Builder Failover (`qwen/qwen3-32b`, `openai/gpt-oss-20b`, `llama-3.1-8b-instant`).
   - **Stage 6 Independent Reviewer Pool (Set B):** Open-weight Gemma 4 (`gemma-4-26b-a4b-it`, `gemma-4-31b-it`) → Groq Reviewer Failover (`llama-3.3-70b-versatile`, `openai/gpt-oss-120b`).
   - `stage6_review.py` asserts at startup that `BuilderSet ∩ ReviewerSet == ∅`, failing fast if any configuration ever introduces overlap. Combined with a 6-point adversarial checklist prompt requiring line-level evidence, this prevents self-agreement bias even under cascading failovers.

## Consequences
Positive consequences include cryptographic/platform-enforced non-push permissions, zero leakage of implementer rationalizations, provable zero-overlap model diversity across every primary and fallback path, and high availability via separate Groq failover pools.

Negative consequences include slightly smaller per-side fallback chains (since models cannot be shared between Builder and Reviewer) and extra CI runner startup overhead (~30–60s per review job).

Neutral consequences include transparent auditing: every PR review displays the exact reviewer model used and links to `review.md` and `review_usage.json`.
